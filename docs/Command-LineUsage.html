Command-Line Usage

DFRefactor and its unit-test runner both support unattended operation from the command line. This enables scripted batch refactoring and continuous-integration use, where no user interaction is possible.


Which executable

This help describes the FlexTron program, DFRefactorFT64.exe, and the examples below use that name. The classic program is DFRefactorx64.exe and takes exactly the same flags.

You rarely type either. Export to ini-file writes the name of the program that produced the file into the ini-file and into the generated PowerShell wrapper, so an exported pair already points at the right executable.


DFRefactor command-line parameters

Syntax rules

  • A flag and its value form a pair separated by a space (for example /sws "C:\Proj\My.sws").
  • Parameters may be supplied in any order.
  • Paths must be enclosed in single or double quotes.
  • Flag spelling is case-insensitive.
  • Each flag must be prefixed with a forward slash (/) or a dash (-).
  • Only the parameters relevant to the run need to be supplied.

Flags

Flag(s)

Value

Meaning

/h, /help, /?, ?

—

Display the parameter help, then exit. Takes precedence over /debug.

/debug

—

Echo every parameter that was received, then exit without refactoring.

/sws

"path.sws"

The workspace file. Mandatory unless /bm supplies an ini-file that names the workspace.

/f, /file

"path"

A single source file (full path). Takes precedence over /sws.

/d, /dirs, /folders

A;B;C

A semicolon-separated list of folder names. These are added to the folders already saved for the workspace, not a replacement. Use together with /sws.

/bm, /batch_mode

"path.ini"

The usual way to run headless. Run the settings held in an ini-file. A bare file name is looked for in DFRefactor's own Programs folder; otherwise pass a full path.

/b, /batch

—

Run the settings already stored for the workspace, with no ini-file. The UI is visible while the run proceeds, but no interaction is required; actions and errors are logged, not shown.

/c, -c, --console

"path.ini"

Superseded by /bm. Still accepted so existing scripts keep running, but no longer the documented form.

Precedence

  • A single source file (/f) takes precedence over a workspace (/sws).
  • An ini-file already names the workspace, folders, filters and functions, so /sws is not needed alongside /bm.
  • If neither /bm nor /batch is given, the program starts, shows the parameters it was passed, and waits — it does not begin refactoring automatically.

Examples

Run all previously selected functions across two folders of a workspace, silently:

DFRefactorFT64.exe /sws "C:\DataFlex 26.0 Examples\Order Entry\Order Entry.sws" /d AppSrc;DDSrc /batch

Run a single file:

DFRefactorFT64.exe /f "C:\Proj\AppSrc\Customer.vw" /batch

Run from a saved ini-file (recommended — see below):

DFRefactorFT64.exe /bm "DFRefactor_Order_Entry.ini"


Using an ini-file

Instead of specifying the workspace, folders, and file filter as individual flags, the entire configuration can be supplied as an ini-file via /bm.

Export to ini-file offers DFRefactor_<Workspace>.ini in DFRefactor's own Programs folder — not the folder of the workspace being refactored. Every workspace you export lands in that one place, which is why the workspace name is spliced into the file name: two workspaces exported side by side cannot overwrite each other. It is also the folder /bm searches when given a bare file name, so an exported ini-file can be run by name alone. Any other name and location will do; supply the full path if you move it. Spaces in a workspace name become underscores, because the path ends up on a command line where an unquoted space is two arguments.

The ini-file has five sections, plus a sixth for build use:

[SWS File Section]

SWS File Name=C:\Proj\My.sws


[User Name Section]

User Name=rdcto


[Folder Section]

Folder Name1=C:\Proj\AppSrc

Folder Name2=C:\Proj\DDSrc


[File Filter Section]

File Filters=*.src;*.vw;*.sl;*.dg;*.rv;*.pkg;*.cl;*.wo;*.dd;*.bp;*.inc;*.nui;*.utl;*.mn;*.mnu


[Functions Section]

Function Name1=ChangeCalcToMoveStatement

Function Name2=ChangeCurrent_ObjectToSelf

Function Name3=ChangeLegacyOperators


[Result Section]

Result File Name=...\Programs\DFRefactor_Order_Entry_RESULT.txt

Notes:

  • [Folder Section] entries are numbered (Folder Name1, Folder Name2, …) and are added to the folders already saved for the workspace.
  • [Functions Section] entries are numbered (Function Name1, …) and must use the exact function names shown on the Refactoring Functions pages.
  • [File Filter Section] uses a single semicolon-separated File Filters value.
  • [Result Section] is optional in a hand-written ini-file, but the export always fills it in, naming <ini name>_RESULT.txt beside the ini-file. See How a build tells whether the run worked.


Exporting settings to an ini-file

Writing an ini-file by hand is error-prone. Instead, configure the workspace, folders, file filter, and function selection interactively, then press the Export to ini-file icon on the toolbar — it sits just after the Refactor Engine Error Log icon, at the head of its own group. This writes a ready-to-use ini-file reflecting the current configuration, which can then be passed to /bm and committed to source control for repeatable runs.

The export also writes a PowerShell wrapper. Beside the ini-file you get <ini name>_RUN.ps1 — for DFRefactor_Order_Entry.ini, that is DFRefactor_Order_Entry_RUN.ps1. It is named after the ini-file rather than fixed, so a folder holding several ini-files gets a wrapper for each instead of them overwriting one another.

The wrapper is pre-filled for that ini-file and ready to drop into a build. It deletes any stale result file, starts DFRefactor headless with a watchdog timeout (30 minutes by default), kills the process tree if that expires, then reads the result back and reports. Its parameters — $Exe, $Ini, $ResultFile, $TimeoutSeconds — can all be overridden; set $Exe to a full path if the executable is not on the PATH. Re-export to refresh it.


How a build tells whether the run worked

A headless run reports its outcome two ways, and a careful build checks both:

  • The result file named in [Result Section]. The run writes STATUS=SUCCESS or STATUS=FAILED to it. A missing file is itself the answer — the run crashed, hung, or never finished — which is why the wrapper deletes it first.
  • The process exit code: 0 on success, 1 on failure.

The generated wrapper treats the result file as the source of truth and the exit code as the cross-check, exiting 0 when both agree on success, 1 when either says otherwise, and 2 when the ini-file it was pointed at does not exist.


Batch-mode behavior

When a run is started with /bm or /batch:

  • The program UI is shown on screen, but no user interaction is required or expected.
  • All actions, and any errors, are written to the log files rather than displayed in dialogs. See the Refactor Engine Error Log and Other Log files toolbar buttons described in Toolbars.
  • Nothing waits for a click — a prompt that would block instead writes STATUS=FAILED and exits non-zero.
  • The program exits automatically when the run completes.


Running the unit-test runner headless

DFUnit_TestRunner64.exe runs DFRefactor's own test suite, and supports a console mode for automated and CI use:

DFUnit_TestRunner64.exe -c -o "results.xml"

Its flags:

  • -c, --console — run the full suite unattended, write the results to the console, and exit the process with 0 when all tests pass or -1 when any test fails.
  • -o, --output "path" — additionally write a JUnit-style XML report. This is the file a CI system reads to show per-test results rather than a single pass/fail. A missing or unusable path exits -1 immediately.
  • -g, --gui — force the interactive UI.
  • -n, --no-autorun — start without running the suite.
  • -h, --help — print the DFUnit version banner and exit 0.

In console mode the runner never returns to a UI; the process terminates as soon as the suite finishes. Without -c / --console it starts in interactive UI mode.

Caution — overlapping flag names. -c and --console mean different things in the two programs: for DFRefactorFT64.exe they are the superseded way to select a configuration ini-file and require a path argument; for DFUnit_TestRunner64.exe they select console / CI mode and take no argument. They are separate programs with independent argument handling.


Example: continuous-integration pipeline

A typical CI sequence:

  1. Once, interactively: configure the workspace and function selection, then Export to ini-file. Commit the ini-file and its _RUN.ps1 to source control.
  2. In the CI job, run the wrapper — it already knows the ini-file, the result file and the timeout:

powershell -File DFRefactor_Order_Entry_RUN.ps1

Or call the executable directly and check the result yourself:

DFRefactorFT64.exe /bm "DFRefactor_Order_Entry.ini"

  1. Run the unit tests and gate the build on the exit code:

DFUnit_TestRunner64.exe -c -o "results.xml"

A non-zero exit code fails the build.
