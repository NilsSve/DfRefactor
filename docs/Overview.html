Overview

DFRefactor modernizes DataFlex source code. It reads your existing source, finds the constructs that a newer DataFlex would rather you wrote differently — or will no longer accept at all — and rewrites them, mechanically, in bulk, and reversibly.

It is written entirely in DataFlex, and is distributed as freeware under an MIT license.


What it is for

Legacy DataFlex code keeps compiling for a very long time. That is a virtue of the language, and it is also the problem: a workspace can sit on constructs that were replaced two or three releases ago and still build without complaint.

Then you move it to a newer DataFlex, and that same code meets one of three fates:

  • It no longer compiles at all. Calls and commands that earlier releases tolerated have since been withdrawn, and the build stops on them. These block the migration outright — until every one is dealt with, the program cannot be built, let alone run. This is usually the bulk of the work in a version move, and it is work DFRefactor does for you: it maps each error to the function that fixes it and hands you the whole set as one list, instead of you meeting them one compile at a time.
  • It compiles, with warnings. Still accepted, but the compiler is telling you it would rather you wrote it differently — and what is a warning in this release is a fair prediction of what is withdrawn in the next.
  • It compiles silently. Obsolete, but nothing objects. No amount of building will ever point you at it, which is why DFRefactor also reads the source directly.

Finding all three is the point. It turns moving a workspace to a current DataFlex into a series of small reviewed steps rather than one long manual edit against a compiler that only shows you the next problem.

It does not restructure your application, rename your objects, or make design decisions. Every change it makes is one a careful developer would make by hand, applied consistently.


The programs

You run one program. The rest are support:

  • DFRefactor — the application. Everything in this help refers to it.
  • TestBench — a workbench for developing and testing a refactoring function of your own, and the home of the JSON Export/Import facility for sharing one. Only needed if you write your own functions; see Welcome to DFRefactor.
  • DFUnit_TestRunner — the unit-test runner for DFRefactor's own function library, bundled so you can run the suite yourself. Not needed for refactoring.
  • DUFUpdateProgram — the database updater. DFRefactor launches it when its own tables need migrating; you never start it directly.


Two routes through the same tools

The Start Center offers a choice, and you can switch whenever you like:

  • Guided refactor — DFRefactor decides what to run. One Check compiles your program and scans the source, then hands you a single list ranked by how much each finding hurts, with what breaks the build at the top. You approve a plan; it runs.
  • Manual refactor — you decide. Pick the folders, pick the functions, run them. No compile required. Best when you already know what you want changed — one cleanup pass, one function across one folder, or a re-run after a hand edit.

They are two routes to the same engine, not two programs. See How to use the Program.


How it finds work

Two independent kinds of discovery, because neither one sees everything:

  • Compile and analyze — DFRefactor builds your program with the compiler you nominate as the target, then matches each error and warning to the refactoring function that fixes it. This finds what the compiler objects to, which on a version move is mostly errors.
  • Analyze Source — a direct scan of your source for obsolete commands, functions and classes. This finds what still compiles silently, which no amount of building would ever reveal.

A guided Check runs both and folds the results into one list. Every lap is recorded, so the counts coming down are visible from one pass to the next — see Modernization Progress.


Nothing happens without your say-so

  • The findings become a plan you read before anything is written — which functions will run, what each is set to, and every file each will touch.
  • Read Only runs the whole thing and reports what would have changed, writing nothing.
  • Every file a run modifies is copied first to a DFRefactor Backup folder in the workspace home folder. Compare Source shows the difference; Revert puts the originals back. See Program Settings for how long backups are kept.


Which DataFlex versions

DFRefactor officially supports the two most recent major DataFlex releases — currently DataFlex 25 and 26. Older releases may work, but are not supported.

That applies to the version you are moving to. The workspace you open can be much older: you nominate the compiler to target, and its version decides which refactoring functions your workspace needs — and which of its constructs have stopped being legal.


Unattended use

The whole configuration — workspace, folders, file filter and function selection — can be exported to an ini-file and run from the command line with no user interaction, which is what makes DFRefactor usable from a build or a CI job. See Command-Line Usage.


A note on Editor functions

Functions of type Editor — One File (EditorReIndent, EditorNormalizeCase) work through the Scintilla editor control, which is an OCX and must be visible to operate. DFRefactor activates the editor view automatically when a run includes one, so the view will come to the front on its own part-way through.
