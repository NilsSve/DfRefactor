How It All Works

This page describes the internal architecture of DFRefactor, for developers extending the function library. End users do not need to read it.


The refactoring engine

The engine (cRefactorEngine, global handle ghoEngine) processes the source. When a run starts it receives a struct holding:

  • the selected refactoring functions
  • the set of source files to process
  • run-time settings - Read Only, count-only, backup configuration

cRefactorEngine extends BusinessProcess. Errors raised during a run are captured and written to the StatLog table rather than interrupting the run, and can be read afterwards from the Refactor Engine Error Log toolbar button.


The class chain

cRefactorApplication handles startup, settings and workspace management. The function library itself is a chain of five classes, each adding one layer:

Class

What it adds

cRefactorUtilities

Low-level reusable primitives - stack helpers, string and array utilities, scope-keyword detection, keyword-array lookups.

cRefactorLexer

The tokenizer, plus comment and string-literal detection, and the lexer state a function can ask about (in a procedure, in a class, inside a multi-line string).

cRefactorExpressionParser

Expression extraction - parenthesised and legacy gt/ge/lt/le/eq/ne - and boolean-indicator parsing.

cBaseFuncLib

Initialisation and error plumbing: _InitializeFuncLib, _AddAllKeyWords, _ClearRefactoringProperties.

cRefactorFuncLib

RegisterInterface and {Description} meta-tag parsing.

oRefactorFuncLib (global handle ghoFuncLib) is the instantiated object built on that chain, and holds every public refactoring function. New functions are added there.

The most important inherited helper is the tokenizer in cRefactorLexer: given one source line it produces a struct array of tokens - keyword, identifier, operator, string literal, comment. Refactoring functions work against that tokenized view rather than matching strings, which is what makes them survive odd spacing, comments and quoted text.


How functions reach the list

The startup meta-data sync scans oRefactorFuncLib.pkg. Every function marked { Published = True } is collected and the Functions data table is updated from its meta-tags - there is no separate registration step. Add the function, decorate it, restart; it appears in Select Functions.


Refactoring function types

Each function declares its type with a { MethodType = ... } meta-tag inside its { Description } block. The engine uses this to decide what shape of data to pass:

MethodType

Signature

Per-call scope

Documented on

eStandardFunction

String ByRef sLine, String sParameter, Returns Boolean

One source line

Standard - Line by Line

eRemoveFunction

String ByRef sLine, String sParameter, Returns Boolean

One source line, for deletions

Remove - Line by Line

eEditorFunction

String[] ByRef asCode, String sParameter, Returns Boolean

Whole file, via the Scintilla editor

Editor - One File

eOtherFunction

String[] ByRef asCode, String sParameter, Returns Integer

Whole file, as a string array

Other - One File

eOtherFunctionAll

String[] ByRef asFiles, String sParameter, Returns Integer

All selected files at once

Other - All Files

eReportFunction

String[] ByRef asCode, String sParameter, Returns Integer

Whole file; no modifications permitted

Report - One File

eReportFunctionAll

String[] ByRef asFiles, String sParameter, Returns Integer

All selected files at once; no modifications permitted

Report - All Files

A Boolean return from a Standard, Remove or Editor function says whether the line or file was changed. An Integer return from an Other or Report function is a count - lines affected, files reported.

Two notes on the table. The engine always passes sParameter, including to a Remove function, so a function that has no use for it may simply declare it and ignore it - or leave it off the declaration entirely, as two of the shipped Remove functions do. And no function in the library currently uses eReportFunction: every report is written as eReportFunctionAll, because a report is nearly always more useful across the whole selection than one file at a time.


Function parameters

A refactoring function takes at most two:

  • The first always carries the source - one line, or an array of lines, depending on the MethodType.
  • The second, optional, is sParameter, filled from the Parameter column of the function grid. Declare its valid values with { EnumList }, its first-use default with { InitialValue }, and per-value help text with { ParamHelp }.

{ InitialValue } is a first-use fallback only. A user's chosen parameter persists across restarts; the startup sync applies the initial value only when the stored one is blank, or is no longer among the { EnumList } values.


Adding a new function

  1. Add it to AppSrc/oRefactorFuncLib.pkg - or AppSrc/UserDefinedRefactorFunctions.pkg for personal additions, which can be marked { Private = True } to keep them out of the JSON export.
  2. Decorate it:

{ Published = True }

{ Description = """

    Human-readable description of what the function does.

    { MethodType = eStandardFunction }

    { SummaryText = Short post-run summary text }

    { FnGroup = Modernization }

    """ }

Every line inside the triple quotes must be indented at least as far as the closing """. A line that starts further left crashes the DataFlex 26 compiler silently - no error, no message, a zero-byte .err file.

  1. { FnGroup } places it in the Select Functions grid - Modernization, Cleanup (shown as Tidy Up) or Unicode64 (shown as x64 + Unicode). Without one it lands in Other.
  2. If the function fixes a compiler message, add { ModRecipe = "<msg#> | <match-text> | [category]" } so the Analyzer can offer it. The category is AutoFix, Suggest or Explain. Repeat the tag for a function that fixes more than one message.
  3. Add { EnumList }, { InitialValue } and { ParamHelp } if it takes an sParameter.
  4. { FnFamily = <name> } collects near-identical converters into a single table on their type's page, rather than giving each one a section of its own. Use it where the example is the whole explanation and the prose would be interchangeable.
  5. { NoDoc = True } keeps a function out of this manual - for one the engine applies automatically on every line, or one that exists for the maintainer rather than the user.
  6. Add unit tests - a fixture in AppSrc/Tests/, or oUnit_Tests.pkg - and run DFUnit_TestRunner.exe to check nothing regressed.

Log files

When a run completes the engine writes its data to the main log, DFRefactorLogFile.txt, in the workspace's DFRefactor_Backup sub-folder - reachable from Read log on the dashboard.

Some functions write logs of their own; UnusedSourceFiles, for instance, lists the files nothing references. Those are reachable from Read other logs.

Errors raised during a run go to the StatLog table, and are read from the Refactor Engine Error Log toolbar button.
